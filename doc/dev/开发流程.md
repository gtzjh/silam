## 开发工作流规范

### 添加新功能模块

#### **步骤1：确定模块层次**
```
问题检查清单：
□ 这是通用功能还是SILAM特定功能？
  → 通用 → 使用.silja.mod.f90
  → 特定 → 使用.silam.mod.f90
  
□ 需要依赖哪些现有模块？
  → 检查是否违反分层原则
  
□ 是否与化学机制相关？
  → 是 → 考虑放入chemistry_manager体系
```

#### **步骤2：创建文件**
```bash
# 示例：添加新的排放源模块
cd source/
touch source_terms_agriculture.silam.mod.f90
```

#### **步骤3：编写模块骨架**
```fortran
module source_terms_agriculture
  !
  ! Agricultural emission source term handler
  !
  ! Code owner: Your Name, email your.name@institution.fi
  !
  ! Units: SI
  ! Code: ANSI FORTRAN-90
  !

  use source_terms_general  ! SILAM源项基类
  use cocktail_basic        ! SILJA物质定义
  use fields                ! SILJA场操作
  
  implicit none
  
  private
  
  public :: init_agriculture_source
  public :: add_agriculture_emission
  
contains

  subroutine init_agriculture_source(source, nlptr)
    ! Implementation...
  end subroutine init_agriculture_source
  
end module source_terms_agriculture
```

#### **步骤4：集成到系统**
修改调用模块（如`chemistry_manager`或`source_terms_general`）：
```fortran
use source_terms_agriculture  ! 添加依赖

! 在适当位置调用新模块接口
call init_agriculture_source(...)
```

#### **步骤5：编译验证**
```bash
# 从当前工作树根目录执行
make -C source
# 检查编译错误和警告
```

按影响范围补充案例运行或数值回归，参见[测试与调试](测试与调试.md)。

### 修改现有模块

先检查目标模块、调用方、配置和现有测试，确定最小改动范围。局部修改可增量编译；接口或依赖变化时，再按需要重新生成规则或清理重编。相关测试覆盖变更行为，不因文档修改而运行模型。

涉及计算公式、单位、关键数值方法或并行行为时，先明确科学解释和验证标准，并按下面的标准询问是否隔离。

### Git工作流

#### 任务大小与分支选择

默认直接在 `main` 开发，主目录保持 `main`。agent 在首次编辑前判断影响范围、实施步骤和验证需求，文件数与行数只作辅助信息。

小任务通常目标单一、边界明确，公共接口和模块职责稳定，使用现有检查即可验证。一个功能点及其配套测试可以仍是小任务。

出现以下任一情况，先询问用户是否创建分支并用 worktree 隔离：

| 判断条件 | 典型情况 |
|----------|----------|
| 多阶段实施计划 | 有多个子目标、实施阶段或验收目标 |
| 跨模块协调 | 多个功能模块需要联动修改接口、共享数据或调用流程 |
| 结构或构建变化 | 模块职责、公共接口、数据格式、工具链或依赖变化 |
| 科学或数值行为变化 | 公式、单位、关键算法、精度或并行计算方式变化 |
| 验证范围扩大 | 新测试体系、验收标准或数值基线变化，或需要明显扩大的验证 |

先只读分析，再给出询问理由、建议分支和目录。用户选择继续在 `main` 后，按该决定执行，不重复询问；范围发生实质变化时再讨论。

#### 经用户同意后的隔离操作

仅在用户明确要求或同意隔离后执行。以下示例从主目录运行：

```bash
# 从已提交的 main 创建任务分支和工作树
git worktree add -b task/example-change .worktree/example-change main

# 已有分支直接检出到工作树，保留其历史
git worktree add .worktree/silam_v6_1pub silam_v6_1pub
```

两条命令是不同用途的示例，按用户同意的任务选择。主目录继续保持 `main`，独立任务使用不同工作树。同一任务的代理按文件分工，主代理协调 Git 写操作。

新工作树不包含主目录未提交、未跟踪或忽略的文件。首次构建前核对本地配置，参见[构建系统](构建系统.md#工作树中的构建配置)。各工作树分别使用自己的配置、构建产物、临时目录和运行输出。

#### commit、合并与 push

agent 可以自行决定本地 commit 时机，只提交本任务预期内容。项目不要求每任务固定一次提交，也不要求任务日志、MEMORY 或日志提交尾注。

隔离任务完成后，先同步最新 `main`，在任务工作树解决冲突并验证受影响内容。报告修改、检查结果和未验证范围，等待用户明确同意后再合并回 `main`。合并前检查主目录的现有改动，保留无关工作。

push 必须另行获得用户明确同意。创建分支、创建 worktree 或 commit 的同意不同时授权合并或 push。

#### 工作树与临时文件清理

隔离任务等待合并期间保留工作树。合并完成后，检查其中的修改、未跟踪文件和被忽略的文件，先保留交付物及用户数据，再用 `git worktree remove` 移除工作树，并删除已合并的任务分支。不要强制删除未合并或未保存的工作。

临时文件统一放在当前工作树的 `.tmp/<任务名>-<YYYYMMDD-HHMMSS>/`，仅在需要时创建。完成后确认路径位于该工作树的 `.tmp/` 内，移出交付物，只删除本任务目录并确认删除成功。保留 `.tmp/` 和其他任务内容；清理失败时报告路径及原因。

#### **不应提交的文件**
```
✗ bin/silam_*           # 可执行文件
✗ obj/**/*.o            # 编译中间文件
✗ obj/**/*.mod          # 模块接口文件
✗ .tmp/**/*             # 临时文件
✗ .worktree/**/*        # 其他工作树的文件
```

已有的 `source/cbm*.f90` 属于主模型依赖，必须保留在 Git 中；当前分发已移除 KPP 生成器目录。

## 提交前检查

- 对照[源码组织与命名](源码组织与命名.md)、[项目结构与架构](项目结构与架构.md)和[代码风格与文档](代码风格与文档.md)审查文件命名、模块声明、分层依赖和代码风格。
- 根据改动范围完成编译和运行验证，参见[测试与调试](测试与调试.md)。
- 使用 `git diff` 审查代码和文档改动，使用 `git status` 确认没有待提交的编译产物或临时文件。
- 架构、接口或构建方式发生变化时，同步更新相关开发文档。

## 新开发者快速清单

### 环境搭建

按[项目说明](../../README.md)安装依赖，按[构建系统](构建系统.md)选择平台配置并构建。记录实际使用的编译器、依赖版本和选项；环境检查与模型验证分别报告。

### 第一次代码修改

1. 检查当前分支、现有改动、相关代码与文档。
2. 判断任务大小，小任务在 `main` 开发；较大任务先询问是否隔离。
3. 实施最小改动，更新必要测试与对应开发文档。
4. 执行适用检查，报告已通过、失败和未验证的范围。
5. 按需要 commit；隔离分支等待用户同意再合并，push 等待用户明确同意。

### 核心规则速查
✓ **DO**：
- 所有源码放`source/`
- 使用`.silam.mod.f90`或`.silja.mod.f90`命名
- 遵循分层依赖（SILAM→SILJA→基础）
- 单位使用SI
- 按改动范围完成必要验证

✗ **DON'T**：
- 创建source子目录
- 提交.o/.mod文件
- SILJA依赖SILAM
- 硬编码常量
- 跳过编译测试
